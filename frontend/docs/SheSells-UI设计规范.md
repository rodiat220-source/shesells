# SheSells UI 设计规范 v0.1

> 目标：把 SheSells 从“能跑的第一版”推进到“有稳定体验语言的 AI 销售教练产品”。
> 本规范先服务 Demo 和第一阶段开发，后续随着真实用户反馈继续迭代。

---

## 1. 设计目标

SheSells 的 UI 不是普通聊天界面。它的核心体验是：BA 正在和顾客对话，同时有一个 AI 教练在关键时刻介入、提醒、暂停、复盘。

因此，第一版 UI 规范要优先解决三件事：

1. 让用户一眼分清三种角色：BA、顾客、AI 教练。
2. 让教练消息明显区别于普通聊天消息，体现“Agent 介入”。
3. 让能力雷达图随每轮回答更新，让用户看见自己的训练变化。
4. 让训练流程稳定可控，尤其是 loading、halt、completed、error 等状态。

前端判断原则：

- 聊天气泡承载“对话内容”。
- 教练卡片承载“训练判断”。
- 状态变化必须由数据驱动，不靠页面自己猜。
- Demo 关键时刻优先级高于装饰性细节。

---

## 2. 产品气质

### 2.1 关键词

- 专业：像一个可信的美妆培训工具，不像娱乐聊天应用。
- 温柔：适合销售顾问训练，不制造压迫感。
- 清晰：评委或用户第一次进入也能马上知道下一步做什么。
- 有介入感：教练不是旁白，而是在关键节点真正影响训练流程。

### 2.2 不采用的方向

- 不做强营销落地页风格。
- 不做过度可爱或游戏化的视觉。
- 第一阶段不做独立 Dashboard 或独立复盘页。
- 不把所有反馈都做成弹窗，反馈应自然出现在对话流里。

为什么：

当前产品的核心价值是“陪练 + 教练判断”。如果 UI 太像营销页，用户会误以为这是介绍产品；如果太像普通 ChatBot，用户感受不到 Agent 的专业性。

## 3. 页面结构

训练页采用三层结构：

1. 顶部 Header：品牌、训练标题、训练状态、返回入口。
2. 主体区域：左侧情境面板 + 右侧对话面板。
3. 底部输入区：BA 输入、发送、结束训练、暂停确认。

### 3.1 Header

职责：

- 告诉用户当前在哪个训练场景。
- 提供返回首页的低干扰入口。
- 展示训练状态：训练中、已暂停、已完成。

规范：

- 高度稳定，不随内容变化跳动。
- 状态文案要和 `session.status` 对应。
- 更多按钮第一阶段可以存在，但不承载核心流程。

### 3.2 左侧情境面板

职责：

- 告诉 BA：顾客是谁、顾虑是什么、训练目标是什么。
- 帮助用户在对话中保持角色感。

内容优先级：

1. 顾客画像。
2. 训练目标。
3. 对话阶段进度。
4. 简短教练提示。

规范：

- 桌面端显示。
- 小屏可以隐藏，避免挤压对话主任务。
- 不承载复杂操作，避免用户训练时分心。
- 可承载实时迷你雷达图，让用户看到每轮回答后的能力变化。

### 3.3 对话面板

职责：

- 承载训练主流程。
- 展示顾客、BA、教练三类消息。
- 根据状态控制输入区。

规范：

- 消息按 API 返回顺序追加，不在前端重新排序。
- 新消息出现后自动滚动到底部。
- loading 时显示顾客/系统正在思考，不白屏。

## 4. 角色消息规范

### 4.1 顾客消息

视觉：

- 左侧排列。
- 灰白或浅暖灰气泡。
- 带顾客头像或“顾客”标识。

语义：

- 顾客消息是训练对象的真实反应。
- 视觉权重中等，不抢教练消息。

### 4.2 BA 消息

视觉：

- 右侧排列。
- 使用品牌主色气泡。
- 带“你”或“BA”标识。

语义：

- BA 消息代表用户刚刚做出的训练动作。
- 要清晰显示，便于后续复盘对照。

### 4.3 教练消息

视觉：

- 左侧或居中偏左展示。
- 不使用普通聊天气泡。
- 使用卡片/提示块，带左边框或强类型色。

语义：

- 教练消息是系统判断，不是顾客对话。
- 它决定 SheSells 和普通 ChatBot 的区别。

工程规则：

```ts
message.role === "coach" && message.coachType
```

满足以上条件时，必须进入教练消息渲染逻辑，不走普通气泡。

## 5. CoachType 视觉规范

### 5.0 实时迷你雷达图

定位：

- 雷达图不是只在训练结束后出现的报告组件。
- 第一阶段应作为训练过程中的实时反馈仪表，每次 BA 回答后更新。
- 结束时的 summary 雷达图是最终结果，训练中的迷你雷达图是过程反馈。

展示位置：

- 桌面端优先放在左侧情境面板中，和顾客画像、训练目标、阶段进度一起构成“训练仪表区”。
- 小屏端可以折叠为简短文字评分，避免挤压对话输入。
- summary 消息内仍然保留最终雷达图，用于结束复盘。

更新时机：

- BA 每发送一条消息后，等待 `/api/chat` 返回。
- 前端从 response 中读取最新五维能力评分。
- 合并到当前 session 状态，并触发迷你雷达图更新。

前后端配合：

```ts
POST /api/chat

Response:
{
  newMessages: Message[];
  updatedState?: Partial<CustomerState>;
  updatedDimensions?: Dimensions;
  sessionStatus: "active" | "halted" | "completed";
}
```

规则：

- `updatedDimensions` 是训练过程中的最新能力快照。
- summary 的 `metadata.dimensions` 是结束时的最终能力结果。
- 如果某一轮没有返回 `updatedDimensions`，前端保留上一轮雷达图，不清空。
- 如果雷达图渲染失败，降级为文字：`倾听 78 · 专业 70 · 推荐 60 · 异议 55 · 共情 72`。

为什么：

实时雷达图能让用户感到“我每一句话都在被训练系统理解和评估”。这比结束后才给报告更像教练，也更符合 Agent 陪练的产品定位。

### 5.1 probe 主动追问

场景：

- BA 跳过探询。
- BA 回复太短。
- BA 急着推荐产品。

视觉：

- 淡黄色或琥珀色边框。
- 低到中等视觉权重。
- 使用灯泡、问号、提示类图标。

行为：

- 不禁用输入框。
- 不阻断对话。

前后端配合：

```ts
coachType: "probe"
metadata.requiresAction: false
```

### 5.2 halt 主动喊停

场景：

- BA 连续忽略顾客关键顾虑。
- 系统需要暂停训练并让用户意识到问题。

视觉：

- 红色或珊瑚色边框。
- 教练消息中最高视觉权重。
- 出现时可以有轻微滑入或强调动画。

行为：

- 输入框禁用并变灰。
- 底部显示确认按钮。
- 按钮文案来自 `metadata.actionLabel`，默认“明白了，继续”。
- 点击确认后恢复输入，不需要额外请求后端。

前后端配合：

```ts
coachType: "halt"
metadata.requiresAction: true
metadata.actionLabel?: string
sessionStatus: "halted"
```

为什么：

这是 Demo 的关键时刻。用户必须明确感到：AI 教练不是只评价，而是在训练过程中真的介入。

### 5.3 feedback 即时反馈

场景：

- BA 做了值得强化或提醒的动作。
- 不需要暂停训练。

视觉：

- 正向反馈用绿色或蓝绿色边框。
- 普通提醒用蓝色边框。
- 视觉权重低于 halt。

行为：

- 不禁用输入。
- 不打断用户继续对话。

前后端配合：

```ts
coachType: "feedback"
metadata.requiresAction: false
```

### 5.4 summary 训练总结

场景：

- 用户点击结束训练。
- 达到最大轮数。

视觉：

- 大于普通教练消息。
- 包含总结文案、评分、关键时刻。
- 可嵌入迷你雷达图。

行为：

- 输入禁用。
- 总结直接出现在当前对话流里。
- 用户可以重新开始训练。

前后端配合：

```ts
coachType: "summary"
metadata.dimensions
metadata.criticalMoments
sessionStatus: "completed"
```

降级规则：

- 如果雷达图不可用，显示文字评分。
- 如果某个维度缺失，不阻断总结渲染。

### 5.5 champion_replay 销冠对比

场景：

- summary 之后展示优秀处理方式。

视觉：

- 使用对比结构。
- “你的回复”使用偏红提示。
- “销冠回复”使用偏绿色提示。
- 技巧说明作为辅助文本。
- MVP 使用 3 段预设对比：探询、异议、促单。

行为：

- 不使用弹窗。
- 在对话流中自然展开。
- 出现在 summary 之后，由 `/api/finish` 一次性返回。

前后端配合：

```ts
coachType: "champion_replay"
metadata.replayTurns
```

为什么：

对比是训练产品最容易让用户“明白差距”的地方。它不能藏在二级页面里，也不能只是一段总结文字。

## 6. 状态规范

训练界面至少有五类状态：

| 状态 | 数据来源 | UI 表现 |
| --- | --- | --- |
| loading | `isLoading` | 禁用发送，显示思考动画 |
| active | `session.status === "active"` | 输入可用，可以结束训练 |
| halted | `session.status === "halted"` 或 halt 消息 requiresAction | 输入禁用，显示确认按钮 |
| completed | `session.status === "completed"` | 输入禁用，在当前对话流中展示 summary 和 champion_replay，显示重新开始入口 |
| error | API 请求失败 | 显示错误文案和重试入口 |

关键规则：

- `halted` 不能只依赖 `sessionStatus`，还要检查新消息中是否存在 `metadata.requiresAction === true`。
- loading 不能覆盖已出现的消息。
- error 不能清空当前对话。
- completed 后不能继续发送消息。
- BA 点击“结束训练”或对话达到最大轮数（MVP 为 12 轮）后，进入 completed。

为什么：

前端专业性很大一部分体现在异常状态。Demo 时用户可能慢、乱、刷新、网络卡顿，UI 必须稳住流程。

## 7. 设计 Token 草案

当前阶段先定义语义 token，不急着追求完整设计系统。

### 7.1 颜色

| Token | 用途 | 建议方向 |
| --- | --- | --- |
| `--color-bg` | 页面背景 | 暖白 |
| `--color-surface` | 卡片/面板背景 | 白色或接近白 |
| `--color-text` | 主文字 | 深暖灰 |
| `--color-muted` | 次级文字 | 中性暖灰 |
| `--color-brand` | BA 气泡、主按钮 | 玫瑰红/珊瑚红 |
| `--color-customer` | 顾客气泡 | 浅暖灰 |
| `--color-probe` | 主动追问 | 琥珀色 |
| `--color-halt` | 主动喊停 | 红色/珊瑚色 |
| `--color-feedback` | 即时反馈 | 蓝绿/绿色 |
| `--color-summary` | 总结 | 品牌暖色 |
| `--color-success` | 正向结果 | 绿色 |
| `--color-danger` | 风险提醒 | 红色 |

### 7.2 字号

| 层级 | 用途 | 建议 |
| --- | --- | --- |
| Display | 首页主标题 | 48-70px |
| H1 | 训练/总结标题 | 28-36px |
| H2 | 面板标题 | 18-24px |
| Body | 正文/消息 | 12-15px |
| Caption | 标签/辅助信息 | 9-11px |

规则：

- 对话消息字号不能太小，真实演示时要能被评委看清。
- 辅助标签可以小，但不能影响理解。
- 不使用随 viewport 缩放的字号。

### 7.3 间距和圆角

建议：

- 页面边距：24px 起。
- 面板内边距：20-30px。
- 消息间距：18-26px。
- 普通卡片圆角：8px。
- 聊天气泡圆角：不超过 16px。
- 工具按钮圆角：8-10px。

为什么：

这个产品是训练工具，不是纯内容网站。间距要让信息清楚，但不能空到像营销页。

### 7.4 动画

允许：

- 新消息轻微上移淡入。
- halt 卡片轻微强调进入。
- loading 三点动画。
- 进度条平滑变化。

避免：

- 大面积浮动装饰。
- 影响阅读的循环动画。
- 过度弹跳。

## 8. 组件规范

建议组件分层：

1. 页面组件：负责布局和路由参数。
2. 容器组件：负责读取 store、调用 API action。
3. 展示组件：只根据 props 渲染 UI。

当前核心组件：

- `ChatContainer`：负责消息列表、滚动、loading。
- `MessageBubble`：负责消息类型分发。
- `BAInput`：负责输入、发送、暂停确认、结束训练。
- `MiniRadar`：负责维度评分展示。
- `CriticalTimeline`：负责关键时刻。
- `ReplayInline`：负责销冠对比。

规则：

- `MessageBubble` 不应该发 API。
- `BAInput` 可以触发用户动作，但不应该关心消息怎么渲染。
- API 字段转换应尽量集中，不散落在多个组件里。

为什么：

这样拆分后，后端改 response 或 UI 改样式时，不会牵一发动全身。

## 9. 前后端协作规范

前端关心的不是“有没有接口”，而是每个接口能否驱动 UI 状态。

### 9.1 创建训练

```ts
POST /api/session
```

前端需要：

- `sessionId`
- `scenario`
- 初始顾客消息或可通过 GET session 获取完整 session

### 9.2 发送消息

```ts
POST /api/chat
```

前端需要：

```ts
{
  sessionId: string;
  newMessages: Message[];
  updatedState?: Partial<CustomerState>;
  sessionStatus: "active" | "halted" | "completed";
}
```

规则：

- `newMessages` 顺序就是渲染顺序。
- 如果返回 halt 且 `requiresAction` 为 true，前端立即进入暂停态。
- 不要求前端理解后端为什么 halt，前端只负责忠实呈现。

### 9.3 结束训练

```ts
POST /api/finish
```

前端需要：

- summary 消息。
- champion_replay 消息。
- completed 状态。
- 最终 `dimensions` 应和训练过程中的实时雷达图口径一致。

## 10. 第一阶段验收清单

### 10.1 视觉验收

- 顾客消息左侧灰色气泡。
- BA 消息右侧品牌色气泡。
- 教练消息不是普通气泡。
- probe、halt、feedback、summary、champion_replay 有明显类型差异。
- halt 是最强视觉状态。

### 10.2 交互验收

- 发送中不能重复发送。
- loading 有明确反馈。
- halt 后输入框禁用。
- 点击“明白了，继续”后恢复输入。
- completed 后不能继续输入。
- API 失败不清空已有对话。

### 10.3 工程验收

- UI 状态由 `session.status`、`coachType`、`metadata` 驱动。
- 消息顺序按后端返回数组追加。
- 组件职责清楚。
- 关键文案不硬编码在多个地方。
- 移动端至少能完成核心流程。

## 11. 待讨论问题

这些问题需要产品和前端一起定：

1. 品牌主色是否继续使用当前玫瑰红，还是更偏专业蓝绿？
2. 首页是否保留当前偏营销的 hero，还是第一阶段直接进入训练？
3. halt 的视觉强度要多强：轻提醒、明显暂停、还是接近系统警告？
4. 移动端是否是第一阶段重点，还是只保证基础可用？
5. 教练消息是否要显示“为什么这么判断”的 reasoning？

---

## 12. 当前建议

v0.1 建议先坚持以下方向：

- 主色继续用温柔玫瑰红，保留美妆行业感。
- 训练页优先于首页打磨。
- 教练消息做成产品视觉核心。
- halt 做成第一阶段最强交互记忆点。
- summary 和 champion_replay 第一阶段只在当前对话流内展示，不跳转独立复盘页。
- 设计系统先轻量化，不提前做复杂组件库。
